# P0.06 — Order / Payment Core

Status: **FINAL VERIFIED — CONCRETE SLICE SPECIFICATION**

1. **Identity:** P0.06; Order/Payment; P0.
2. **Objective:** separate purchase intent from financial settlement and establish safe payment integration.
3. **Scope:** order item/commercial snapshot, payment attempt/state, mock provider, refund request, webhook idempotency and reconciliation. Fulfillment remains separate.
4. **Sources:** Core Contract #5; Phase 4 SoT; locked billing/provider decisions.
5. **Dependencies:** P0.04 currency; P0.05 product/entitlement; P0.08 storage where applicable; P0.09 events.
6. **Architecture:** Order owns purchase intent/state; Payment owns settlement/refund; provider adapter does not own business state.
7. **Ownership:** Order, Payment and Fulfillment are distinct authorities.
8. **Data model:** Order, order item/commercial snapshot, payment attempt/state, provider reference, refund request and reconciliation context per Contract #5.
9. **State:** order lifecycle and payment lifecycle remain separate; ambiguous provider result enters reconciliation.
10. **API:** create/read order, initiate payment, receive provider result/webhook, request refund; exact schemas follow canonical API registry.
11. **UI:** order/payment status, retry and failure states; never present ambiguous provider result as success.
12. **Events:** OrderCreated and PaymentPaid plus approved payment lifecycle events; P0.09 owns transport.
13. **Workers:** webhook/event handlers use retry/DLQ and idempotency.
14. **Security:** server-side authorization; provider credentials never exposed to client.
15. **Configuration:** provider configuration follows approved configuration/security authority.
16. **Storage:** persist order/payment state and provider references; payment evidence follows storage authority where applicable.
17. **Observability:** correlation, order/payment/provider reference and outcome classification without secrets.
18. **Errors:** amount/currency mismatch, duplicate webhook, provider failure and reconciliation-required outcome use canonical errors/states.
19. **Idempotency:** payment attempt and webhook processing must be safe under duplicate delivery/retry.
20. **Tests:** order→payment, paid→fulfillment handoff, duplicate webhook/attempt, amount/currency mismatch, failure and safe retry.
21. **Acceptance:** no paid order grants entitlement twice; ambiguous provider result is never silently finalized.
22. **Gate:** contract, state, provider and entitlement handoff verified before build.
23. **Checklist:** [ ] order schema [ ] payment state [ ] webhook [ ] idempotency [ ] reconciliation [ ] tests.
24. **Exit:** order/payment boundary locked for manual and provider payment flows.
25. **Risks:** duplicate/ambiguous provider callbacks can cause double settlement or entitlement grant.
26. **Open Decisions:** none introduced.
