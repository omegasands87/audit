# P0.04 — Market / Localization / Currency

Status: **FINAL VERIFIED — CONCRETE SLICE SPECIFICATION**

## 1. Slice Identity
ID: P0.04. Domain: Market/Localization/Currency. Priority: P0.

## 2. Objective
Establish market-aware language and currency behavior using approved commercial rules.

## 3. Scope / Out of Scope
**In:** market, language, currency, fallback and explicit pricing currency. **Out:** new commercial currency rules or pricing policy.

## 4. Source Documents
Locked business decisions; approved product authority; Phase 4 Source of Truth; Phase 5 corrections; implementation specification framework.

## 5. Dependencies
P0.00 architecture; P0.03 configuration where applicable; P0.05 product/pricing/entitlement.

## 6. Architecture Boundary
Localization and currency selection are consumed by product/pricing and UI layers through approved application boundaries; they do not redefine commercial ownership.

## 7. Domain Ownership
This slice owns market/localization/currency resolution. Product owns sellable definitions and prices; entitlement owns granted rights.

## 8. Data Model
Required concepts: market, locale/language, currency, fallback and explicit pricing currency. Minimum approved foundation is ID/EN and IDR/USD.

## 9. State Machine
Resolution outcomes: explicit selection → resolved market/locale/currency, with approved fallback when required. No alternate commercial rule is inferred.

## 10. API/Application Contract
Operations resolve market, locale and currency; product/pricing consumes explicit resolved currency. Exact endpoint schemas remain under canonical API/contract authorities.

## 11. UI/UX Scope
Locale and currency presentation must be explicit and market-aware; loading, fallback and invalid-selection states must be handled without silently changing commercial currency.

## 12. Event Contract
Only approved market/localization changes are observable; no new event semantics are introduced here.

## 13. Worker/Job Scope
No mandatory worker. Asynchronous propagation, if any, follows platform event/retry rules.

## 14. Security/Authorization
Market/currency selection must not bypass authorization, entitlement or tenant boundaries.

## 15. Configuration
Approved market/localization values may be configuration-backed, but configuration cannot create an unapproved commercial rule.

## 16. Storage
Persist only the market/locale/currency state required by the approved product model and user/account context.

## 17. Observability
Record resolved market/locale/currency and correlation context without sensitive data.

## 18. Error Handling
Invalid or unsupported combinations use canonical errors and approved fallback behavior; do not silently substitute an unapproved commercial currency.

## 19. Idempotency/Concurrency
Repeated resolution is deterministic for the same context; persisted changes use standard idempotent application semantics.

## 20. Test Specification
Indonesia → IDR/ID; Global/Test → USD/EN; fallback behavior; explicit pricing currency; unsupported combination handling.

## 21. Acceptance Criteria
Approved market and locale resolve correctly, currency is explicit, fallback is deterministic, and no new commercial currency rule is introduced.

## 22. Acceptance Gate
All behavior must trace to locked business/product authority before implementation.

## 23. Implementation Checklist
- [ ] market resolution verified
- [ ] ID/EN locale foundation verified
- [ ] IDR/USD currency foundation verified
- [ ] fallback tested
- [ ] explicit pricing currency tested
- [ ] no unapproved commercial rule introduced

## 24. Exit Conditions
Market/localization/currency foundation is stable for downstream product and UI slices.

## 25. Known Risks

## 26. Open Decisions
None introduced. Existing locked business decisions remain authoritative.
